Partie 1 · Cloud Computing

Le Cloud : des ressources à la demande

Le cloud = louer des ressources informatiques au lieu de les posséder.

  • Des serveurs, stockage et logiciels via Internet.
  • Vous payez à l'usage, sans acheter le matériel.
  • Azure entretient l'infrastructure à votre place.
  • Accessible depuis un navigateur, à tout moment.
Avant — creuser son puits
Vous achetez, entretenez, et attendez s'il tarit.
Aujourd'hui — ouvrir le robinet
L'eau arrive, vous payez ce que vous consommez.
Exemple : un fichier sur OneDrive, ouvert sur PC, mobile et tablette.

Analogie : « Avant, pour avoir de l'eau, vous creusiez votre puits : vous l'achetiez, vous l'entreteniez, et s'il n'y en avait plus, vous attendiez. Aujourd'hui, vous ouvrez un robinet : l'eau arrive, vous payez ce que vous consommez, et quelqu'un d'autre entretient le réseau. Le cloud, c'est exactement ça, mais avec des serveurs. »

Les 5 caractéristiques officielles, à citer oralement sans les projeter : libre-service à la demande, accès large par réseau, mutualisation des ressources, élasticité rapide, service mesuré.

Insistez sur « louer » plutôt que « acheter » : c'est le changement mental clé. Transition : « Si on achète plus de serveurs, comment ça se passe concrètement ? »

On-Premise signifie « chez vous » : vos serveurs sont dans votre salle informatique. Vous achetez, branchez, mettez à jour, réparez. Dans le cloud, vous louez une capacité chez Microsoft.

Coût : expliquez CAPEX (gros investissement initial) contre OPEX (facture mensuelle). Nuance sur le contrôle : ce n'est pas « vous n'avez plus le contrôle », c'est un contrôle partagé — vous gardez données, accès et règles ; Microsoft gère la salle, l'électricité et le matériel.

Si un participant dit « le cloud coûte plus cher » : cela dépend de l'usage. Un serveur peu utilisé coûte souvent moins dans le cloud ; un serveur stable et saturé peut être moins cher en local (voir slide 15).

IaaS · Azure Virtual Machines

  • Un serveur complet, mais virtuel.
  • Vous choisissez l'OS, la taille, les disques.
  • Vous gardez la main sur le système.
  • Idéal pour migrer une application existante.

Virtual Machine

CPU · RAM · disques · Windows ou Linux

Responsabilité partagée
Vous : OS, logiciels, données
Azure : serveur, réseau, site
Exemple : une VM Linux « B2s » pour héberger le site interne.

Une machine virtuelle est un ordinateur logiciel : vous vous connectez dessus comme sur un serveur physique, avec les mêmes commandes. Azure fournit la machine, vous fournissez ce qu'il y a dedans.

À citer : les tailles (« B2s », « D4s_v5 ») combinent CPU et mémoire ; Windows et Linux sont disponibles ; on peut redimensionner sans réinstaller, mais il faut redémarrer.

Cas d'usage : « lift and shift », déplacer une application telle quelle sans la réécrire. Mise en garde : vous devez toujours appliquer les mises à jour de sécurité de l'OS.

Partie 1 · Cloud Computing

Cloud : 4 avantages, 4 limites

Avantages

  • Coût ajusté à l'usage réel
  • Montée en charge rapide
  • Maintenance déléguée
  • Accès depuis partout

Limites

  • Dépendance au fournisseur
  • Coûts imprévisibles si mal suivis
  • Compétences et sécurité à maîtriser
  • Données : résidence et conformité
Exemple : une VM oubliée allumée le week-end coûte quand même.

Je veux donner une image équilibrée : le cloud n'est pas magique. Il déplace une partie du travail, il ne le supprime pas.

Dépendance : le « verrouillage » — plus vos données et outils sont spécifiques à un fournisseur, plus il est difficile de partir. Coûts : une ressource oubliée continue de facturer. Compétences : il faut savoir configurer accès, réseaux, sécurité. Données : certains pays imposent la résidence sur leur territoire, d'où le choix de la région (slide 9).

Transition : « Passons à la plateforme concrète qui va nous servir de fil conducteur : Microsoft Azure. »

L'abonnement est le niveau le plus haut : c'est là que la facture arrive, que les droits d'accès sont donnés et que les quotas s'appliquent. Dedans, on crée des groupes de ressources : des dossiers logiques, pas physiques. Et dedans, les ressources : une VM, une base, un réseau.

À citer : un groupe peut contenir des ressources de régions différentes, mais on recommande de le gerer par projet et par région. Le nom RG-Projet-Web est une convention : préfixe RG-, puis le projet.

Informations vérifiées le 23/11/2026 sur Microsoft Learn (page « What is Microsoft Foundry ? », mise à jour septembre 2026) :

Pay-as-you-go, littéralement « payez pendant que vous l'utilisez ». On ne paie pas une machine pour un mois entier si on ne s'en sert que 8 heures par jour. Le calcul est volontairement simplifié à 0,10 € de l'heure.

Vérifiez les calculs à l'oral : 8 × 22 = 176 h → 17,60 € ; 24 × 30 = 720 h → 72 € ; écart 54,40 €, arrondi à ≈ 54 €.

Nuances : le prix réel dépend de la taille de la VM, de la région, du système d'exploitation et des remises (réservations, instances spot). Arrêter une VM supprime la facturation du calcul, mais le disque continue d'être facturé. Présentez le calculateur de prix Azure comme outil à utiliser avant création.

Ne donnez pas de chiffre officiel : le tarif est explicitement fictif.

Métriques et journaux au même endroit.
Alertes
Un message quand un seuil est dépassé.
Tags
Des étiquettes pour retrouver et classer.
Azure Policy
Des règles appliquées à tout l'abonnement.
Exemple : une alerte à 80 % de CPU prévient l'équipe par e-mail.

Une phrase par outil, à développer oralement :

  • Azure Monitor : plateforme de télémétrie — métriques (CPU, mémoire, requêtes), journaux, tableaux de bord. C'est la source des informations.
  • Alertes : une condition (« CPU > 80 % pendant 10 minutes ») et une action (e-mail, Teams, webhook). L'alerte prévient, elle ne corrige pas.
  • Tags : paires clé/valeur, par exemple projet=web et environnement=test. Servent à retrouver des ressources et répartir les coûts.
  • Azure Policy : règles « doit être » — interdire des régions, exiger un tag. La politique peut auditer ou refuser une création.

Ordre logique : Monitor observe, Alertes prévient, Tags classe, Policy impose.

Coûts et quotas : éviter les mauvaises surprises

  • Cost Management analyse les dépenses par service.
  • Un budget fixe un plafond de dépense.
  • Des alertes préviennent à 50 %, 80 %, 100 %.
  • Les quotas limitent les ressources par région.

Exemple : quota de 10 VM en France Central → demander 20 VM.

Cost Management répond à « où passe mon argent ? ». Le budget pose une limite ; les alertes préviennent avant de dépasser. Attention : un budget ne bloque pas automatiquement les dépenses, il informe.

Quotas : limites fixées par abonnement et par région, propres à chaque type de ressource (VM, cœurs GPU, IP…). Si une création échoue avec « quota exceeded », faites une demande d'augmentation dans le portail : Quota → New Quota Request (ou via le support pour certains services).

Bon réflexe : vérifier les quotas avant un projet, pas le jour du déploiement. Les quotas peuvent être augmentés, contrairement à un budget qui est un choix interne.

Question d'ouverture : et si votre application passait du serveur local au cloud demain ?

On peut résumer la session en une phrase : « le cloud délègue l'infrastructure, pas la responsabilité. »

Relisez les cinq points rapidement, sans nouvelle explication, puis lancez la question ouverte : « Si votre application passait au cloud demain, par quel service commenceriez-vous ? »

Réponses attendues : une VM pour migrer (IaaS), App Service pour repartir du code (PaaS), Microsoft 365 pour un usage prêt à l'emploi (SaaS). Validez toutes les réponses cohérentes : l'objectif est de faire réemployer le vocabulaire.
